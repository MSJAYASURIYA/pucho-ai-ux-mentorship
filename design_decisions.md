# Design Decisions and Rationale

**Project:** Pucho.ai — Trust-first automation concept  
**Document purpose:** Explain the main prototype choices and the assumptions behind them.

## Product direction

The concept is built around one idea: a person should be able to understand and review an automation before it is allowed to do something consequential. The experience follows this sequence:

**Describe → Review plan → Review access → Preview → Inspect result**

This is a student UX concept. It is not an official Pucho.ai interface and does not connect to live AI services or external accounts.

## Key decisions

| Decision | Why it is included | Risk or trade-off | What should be validated |
|---|---|---|---|
| Begin with an everyday-language request | Gives users a starting point without requiring workflow terminology. | A short request may not include enough detail to create a safe plan. | Can users describe a task clearly, and what follow-up questions do they expect? |
| Show a step-by-step plan | Makes the proposed process easier to inspect before access is reviewed. | A fixed example may look more intelligent than the prototype actually is. | Do users understand the steps and recognise that this demo uses a scripted plan? |
| Separate permissions from the plan | Makes data access a deliberate decision rather than a hidden setup detail. | Several toggles can still be confusing if their effects are not obvious. | Can users explain what each access toggle permits and what changes when it is disabled? |
| Require explicit confirmation before the demo proceeds | Encourages users to review both access and the example output. | Confirmation checkboxes can become a routine click if users do not understand them. | Do users read and understand the confirmations, or simply click through? |
| Keep outgoing communication as a draft by default | Reduces the chance of an unwanted message being sent in a real implementation. | A real product would need a clear and reliable approval and sending model. | Do users understand the difference between preparing a draft and sending it? |
| Flag uncertain lead matches for review | Avoids presenting a weak inference as a definite decision. | Users need to understand why a case was flagged and how to resolve it. | Can users find the uncertain item and tell what needs checking? |
| Use fictional preview data and label the demo | Lets reviewers inspect the intended flow without connecting private accounts. | Simulated success does not prove a live integration would work. | Do users recognise the limitations and avoid mistaking sample data for real records? |
| Show a result screen with a short run summary | Helps users understand what the demo completed and what needs attention. | The current result screen is scripted and is not a real execution log. | Which status details would users need to decide whether to retry, edit, or stop? |

## Scope decisions

### Included in this concept

- A plain-language task prompt
- A suggested workflow represented in everyday terms
- App-access toggles and an approval choice
- Fictional output preview
- A simulated run summary
- Basic back, edit, and restart paths

### Not included in this concept

- A live AI model
- Real account sign-in or app permissions
- Reading or changing real spreadsheet records
- Sending messages to Slack
- Real run history, audit logs, or failure recovery from connected services

These limits are stated so the prototype can be reviewed as an interaction concept without implying that integrations have been implemented.

## Known design limitations to address

1. The plan is scripted, so the interface should consistently describe it as a **suggested demo plan**, not as a plan generated by a live AI model.
2. Sidebar items such as Workflows, Agents, Connections, and Run history are visual navigation examples; their destinations are not implemented in this prototype. They should be made clearly non-interactive or implemented before the interface is presented as a fuller product.
3. The restart interaction should return all controls to their default state, not only clear the two confirmation checkboxes.
4. The design should be tested with target users before claiming that it is easy to use or that it improves trust.

## How success should be judged

The next iteration should be judged by observed user behaviour, not by the number of screens or the visual finish alone. In particular, users should be able to explain what the workflow will do, which information it will use, whether an external action will occur, and what they can do when something looks wrong.
